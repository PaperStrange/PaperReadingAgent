### 2.2 红线机制（**触碰即死**）

> 用户 2026-09-21："额外增加红线触碰即死机制（硬核红线举例：**文件丢失、卡片内容飘移、测试结果假绿**）"。

| 红线 | 定义 | **可检测判据**（否则"即死"无法触发） |
|---|---|---|
| **R1 文件丢失** | 任何文件/内容被静默删除、截断、少写（含"锚点行被吞"型） | ① 编辑后**结构校验**（标题数/标题层级序列、表格行数、卡号序列无跳号）② 提交前 `git status` + `git diff --stat` 与预期比对 ③ 破坏性操作（`switch -f`/`reset --hard`/`clean -fd`/`rm -rf`/`branch -D`）**前置断言"工作树干净或已提交/stash"**，否则拒绝 ④ 恢复演练：`git reflog` / `stash list` / 操作前补丁快照 |
| **R2 卡片内容漂移** | 同一事实在多处不一致，或卡片状态与事实不符 | ① `TG-14` 的 `verify/verify_card_index.py`（索引↔文件↔状态）② `TG-12` 的派生事实 SSOT + 漂移闸门（数字/状态一致性）③ 反向对照：人为改一处 → 必须 FAIL |
| **R3 测试结果假绿** | 断言在旧实现/目标环境上**不会** FAIL，或断言从未在 CI 执行 | ① **反向对照**（新检查必须先在旧实现上跑出 FAIL）② 断言必须在 **CI 同款环境**跑过（本轮 `RUNNER~1` 事件实证）③ 关键闸门做**变异测试**（去掉修复 → 断言应 FAIL） |

**即死后的动作（草案）**：**立即停止本 Sprint 的功能性推进** → 冻结 → 定位 + 修复 + 反向对照 → 由用户二次确认 → 才恢复。红线事故记入 Sprint §9 与 `A-M11` 卡内实例清单。

## 5. 抽查机制（用户 2026-09-21：我做抽查、**按双盲**；判断类由用户二次检查）

**双盲协议（草案）**：
1. **样本空间预先登记**：抽查对象 = 本期全部 `agents/runs/**` 报告（run_id 清单在抽样前落盘，作为"抽样池"）；
2. **抽样规则先定后抽**：`Get-Random -SetSeed <固定种子>` 从抽样池抽 **3 份**（规则与种子在抽样前写入 Sprint 文档，**抽样后不得更换样本**）；
3. **单盲（对子代理）**：被抽查的子代理**不知道**自己会被抽查，也不知道抽查判据；
4. **双盲（对我）**：**不预先看结论**——我先按原始 spec 独立复核抽取样本的关键断言（含必要时按原命令复现），**得出我自己的结论后**再与报告原文比对，记录"一致 / 不一致 / 无法判定"；
5. **判断类二次检查**：凡涉及"是否算违规""是否算假绿""是否算红线"的**判断**，一律**升级给用户裁定**，我不自行结案；
6. **留痕**：抽查记录（种子、样本、我的独立结论、与原文差异、用户裁定）写入 Sprint §9。

**已知局限（须如实写入报告）**：样本量 3 份、以"关键断言复核"为主（非全文重审）；抽查频率每 Sprint 一次；**抽查本身也受"验证可信度"约束**（抽查脚本/命令须可复现）。
