**待立教训（关闭期 `lessons-learned` 统一编号；期中不插入，以免 "49/63" 口径漂移）**：
① **"工具失败 ≠ 环境失败"**——harness `web_fetch` 全阻时，子代理把"核查手段缺失"写成"全部依赖未通过"；**进程级探针**（同机 `urllib` 直连 PyPI/npm/OSV = 200）证明是工具限制 → 教训：**任何"无法执行"的结论前先做可达性探针**。
② **非 ASCII 内容禁止走 CLI 参数**（走文件/JSON），否则落库即乱码（本轮 `task_id` 实证；与"含反引号的 commit 消息走 `-F <file>`"同源）。
③ **子代理的 finding 是"主张"，不是"事实"——必须独立复验后才动手**（TG-15 复核批实证）：一查 doc-audit 对 `verify_no_policy_hardcode.py --dir` 的判断是"恒 return 0 的 fail-open"，我实测真相是**打印时 `KeyError: 'file'` 崩溃**（根因在 `scan_file` 没给 findings 盖契约字段）——两种失效形态的修法完全不同；若照单全收就会修错地方。**纪律**：每条 finding 先跑一遍最小复现，再决定修法；复验结果与被报不符时，**以实测为准并在记录里写明差异**（本轮已如此记录）。
④ **闸门的断言必须驱动"真实入口"，不能只读代码判断它会不会 fail-closed**（同批实证）：`--dir` 分支的退出码此前只被"读了一眼 return 语句"确认过，而真正的缺陷（缺 `file` 键即崩）在 `print` 处；修法是**用子进程跑真实 CLI 并断言 rc**（现已加入 3 条该形态断言）。同源：TG-15 的 C3 空区间 critical——"锚点==HEAD 时零提交受检却打 ✔"，正是"判定条件在空输入下恒真"的经典形态。
