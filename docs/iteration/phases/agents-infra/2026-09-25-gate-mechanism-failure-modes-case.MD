# 闸门/机制失效模式案例集（agent-infra 反例留档，2026-09-25 用户定规）

> **来源与定位**：用户 2026-09-25 追加定规——"**机制缺口同样记录为 agent infra 的反例**"（原规则只覆盖子代理派单）。
> 本文件是**闸门与机制类**反例的**唯一落点**（一案一节，节号即案例号）；每条必须含 **6 要素**：现象 / 证据（可核）/ 根因 / 机制（已落或待落）/ 反向对照 / 复用面。
> 姊妹文件：`2026-09-25-subagent-dispatch-failure-modes-case.MD`（派单类）、`2026-09-23-edit-boundary-incidents-case.MD`（编辑边界）、`2026-09-23-subagent-scope-breach-case.MD`（越界改写）。
> 由本文件派生的规则条文写入 `docs/1-WORKFLOW.MD` §6；机制侧的执行卡 = `TG-19`（关闭税机制化）、`TG-17`（闸门可信化收尾）。
>
> **共同根因（先说总账）**：这些缺口**不是"没查到"，而是"报了错的话"**——闸门在自身失效时**仍然打印成功**。四类母题：① 判定**自我指涉**（用自己造的东西证自己）；② 判定**空转**（空输入/被剥离/被跳过 ≠ 不通过）；③ 阈值**自证**（上限由被约束者自己声明）；④ **读数手抄**（数字离开工具就失去可核性）。

## 案例 1｜自指断言：闸门"证明"的是自己造的探针，而不是真实产物

- **现象**：`verify/verify_artifact_paths.py` 自检⑥ 断言"**我的探针名不在**产物目录里"——它构造探针、自己检查探针消失。于是**真实的 TG-9 泄漏产物（别的机制留下的运行态 JSON）无法让它变红**，闸门长期 rc=0。
- **证据**：二查 `run-2026-09-25-code-review-071` 的 major（`verify_artifact_paths.py:763-765`；同批 4 条"检查在说假话"之首）；修复后新增"真实产物扫描"分支并带反向对照。
- **根因**：把"**我能自证**"当成"**我验证了系统**"。判定所需的事实**由判定者自己生产** ⇒ 恒真。
- **机制（已落）**：改为对**真实仓库状态**取样（扫描 `git status` + 忽略规则 + 真实产物路径），并新增独立反向对照（真放一个未忽略的产物 ⇒ 必须 FAIL）。
- **反向对照**：修复前/后对"真实泄漏产物"各跑一次（修前 PASS、修后 FAIL）；见 `3-LEARNED` **1.64**。
- **复用面**：凡"自检/冒烟/探针"类判据——**问一句：这条断言失败时，是系统坏了还是探针坏了？**若两者都可能是"探针问题"，它就不是判据。

## 案例 2｜裸 `assert` 在 `-O` 下被整体剥离 ⇒ 断言全空转但仍打印 `ALL PASS`

- **现象**：所有闸门的判定都写成裸 `assert`；`python -O` / `PYTHONOPTIMIZE=1` 下 `assert` 语句被**整体剥离** ⇒ 闸门"跑完、无失败、打印 `ALL PASS (N assertions)`"，而**一条断言都没执行**（连 N 都可能是陈旧的）。
- **证据**：二查 `run-2026-09-25-code-review-071` 的 minor（`verify/verify_lint.py:83` 同型 5 处）；修复后 `verify/verify_gate_integrity.py` 用**真实 `-O` 子进程**探针验证"必须非零退出且不得打印 ALL PASS"。
- **根因**：把"断言"当成语言特性用，而不是当成**判定的载体**；且当时的守卫写法（`assert __debug__`）**本身也会被剥离**。
- **机制（已落）**：8 个闸门加显式分支守卫（`if not __debug__: raise SystemExit(...)`），`verify_gate_integrity.py` 里跑**真实 `-O` 探针**（非模拟）。
- **反向对照**：`python -O <gate>` 必须非零、且输出**不含** `ALL PASS`（真实子进程，非函数注入）。
- **复用面**：任何"退出码即结论"的脚本——**结论必须落在进程退出码上，且要有一条"最优化/降级环境下仍有效"的证明**；见 `3-LEARNED` **1.65**。

## 案例 3｜空扫描集 ⇒ PASS（两侧同源的自洽式判据）

- **现象**：`md_tables` 的"应扫 N / 实扫 M"两侧**都由同一份政策声明派生**。在没有 `docs/iteration/` 的树里（`origin/main` 检出），它打印 **应扫 8 / 实扫 8 → PASS**；同一份政策在 `windows` 上是 **164 / 164**。⇒ **少审 156 个文件**这件事在读数里不可见。
- **证据**：主代理 2026-09-25 实测——`git worktree add <tmp> origin/main` 后 `verify/verify_md_tables.py` rc=0 且打印 `MD-TABLE PASS（8 个文件解析通过）`；政策实读 `md_table_globs` 不含 `agents/runs/**`、`roots=['docs','verify']`（**原卡片条目 3 的"163 vs 1"数字与"含 agents/runs"均为重建值，已更正**）；同族既有实例：`code-review-067:68`（空扫描集 PASS）。
- **根因**：判据是**自洽式**（自己和自己比）而不是**覆盖式**（声明与现实跨源比）。`roots` 层的"目录缺失 fail-closed"只管 `docs`/`verify` 这一层，**管不到整棵子树**。
- **机制（**已落 2026-09-25 D5**）**：`TG-17` 条目 3——`agents/policy.json::md_table_coverage.conditional_roots` 声明"按分支可能不存在的子树"，判据用 `git ls-tree HEAD` 的**直接证据**区分"分支本就没有"（⇒ 具名 SKIP，判决行不得再打 `PASS`）与"本分支上被删"（⇒ FAIL）。三形态真跑实测：windows `PASS 171 文件`／删条件根 ⇒ `rc=1` 点名被删／main 形态 ⇒ `MD-TABLE SKIP（8 个文件…不是通过）`。
- **反向对照**：删除/替换一棵声明过的子树 ⇒ 必须具名（修前 PASS、修后 SKIP/FAIL 各一条）。
- **复用面**：一切"扫描/覆盖/清单"类闸门——**当输入可以为空时，先问"空输入会打印什么"**。

## 案例 4｜SKIP 之后仍打印成功横幅（把"没查"说成"查过了"）

- **现象**：`verify/verify_card_index.py` 在分支无 `docs/iteration/` 时先打印 `SKIP[no-iteration-docs]`，**紧接着**仍输出 `CARD-INDEX PASS：索引↔卡文件一一对应（含…状态三处一致…）` ——那条横幅把**四条被跳过的判据**说成通过了。
- **证据**：复核 `run-2026-09-25-code-review-080` finding **F1**（minor）；`TG-17` 条目 6；同族需自查的闸门：`verify_ledger_measurement`、`verify_agentops` M-g、`verify_close_readiness`。
- **根因**：`SKIP` 只改了**退出路径**，没改**输出契约**；横幅文案是硬编码常量，与本次实际执行了哪些判据无关。
- **机制（待落）**：`TG-19` M-B——SKIP 生效时必须**抑制/替换**横幅（`CARD-INDEX SKIP（分支无该目录）`），并逐个闸门自查文案。
- **反向对照**：分支无该目录时输出**不得**含 `PASS`（修前含、修后不含，各一条真实分支实测）。
- **复用面**：所有"缺数据即跳过"的闸门——**横幅必须由本次执行结果生成，不能是常量**。

## 案例 5｜棘轮上限高于实测值 = 给新增违规发"静默配额"

- **现象**：可读性棘轮 `caps` 一度高于实测（**时点读数（2026-09-25 修复前）**：`E501` 上限 2631、实测 2615）⇒ 在此期间**新增 16 处超长行仍判 PASS**；这类"上限留余量"在多次交付里反复出现。
- **证据**：一查 `run-2026-09-25-doc-audit-070` finding 5 型（cap 与实测不一致）；`agents/policy.json::lint_readability_ratchet` 现为**零余量**（`D101 12/12、D102 46/46、D103 205/205、E501 2494/2494`，实测总数与 `Σcaps` 机器核对）；`3-LEARNED` **1.66**。
- **根因**：把 `cap` 当"容忍度"而不是"**实测快照**"；且"实测值"没有入库 ⇒ 无法机器判定 cap 是否仍等于实测。
- **机制（已落/待落）**：已落——`verify_gate_integrity.py` 断言 `measured_total == Σcaps`；待落（`TG-19` M-C）——每条棘轮必须存 `measured_value` + `measured_at`，改 `cap`/`measured_value` 必须带 `rebased_at` + 理由。
- **反向对照**：把某条 cap 抬 1（不改代码）⇒ 必须 FAIL；`measured_total ≠ Σcaps` ⇒ 必须 FAIL。
- **复用面**：一切"基线/上限/白名单"——**上限必须等于实测，且实测值本身入库**。

## 案例 6｜棘轮只与 `git HEAD` 比较 ⇒ 提交态的放宽成为新基线

- **现象**：棘轮单调性检查只拦"**未提交**的上调"。一次**已提交**的放宽会被当成新基线（`measured_total` 也可同步抬），从此再也无人能看出它被放宽过。
- **证据**：复核（`run-2026-09-25-code-review-074`~`-079` 的 backlog 小节，机制缺口 2）；修复前的比较实现只对 `git HEAD` 逐项比。
- **根因**：把"版本控制"当成了"不可篡改性证明"——**提交本身不是审计**。
- **机制（待落）**：`TG-19` M-C 的 `measured_value` + `rebased_at` + 理由三件套（无理由即 FAIL）。
- **反向对照**：在**提交态**上调 `caps.E501` ⇒ 必须 FAIL（现有实现会通过，这正是缺口）。
- **复用面**：所有以"历史基线"为依据的闸门——**基线的变更必须留下带理由的事件**。

## 案例 7｜判定域取"全局最新一条" ⇒ 跨 Sprint 翻滚，一个合法登记把上一 Sprint 的读数打成噪音

- **现象**：`verify_close_readiness.py::scope_step_run()` 取"作用域步骤**全局最新**的那条 run"，**没有 Sprint 身份**。G2 的 kickoff 〇查（`run-2026-09-25-impact-assessment-081`，一个**完全合法**的登记）一落账本，Sprint-17 的关闭读数即由 **1 项 → 99 项**（其中 **98 项假红**：`[linkage]`65 + `[C1]`33 + `[窗口/次序]`1）。同时**推翻该闸门 docstring 的"真数据零假阳性"自述**。
- **证据**：`sprint-17.md` §9.4（触发 run、复现命令、反事实）；`TG-17` 条目 8；账本 `started_at=2026-09-25T09:09:30+00:00`。
- **根因**：判定的**域**不是从**被判定物**派生，而是从"账本里最新的一条"派生 ⇒ 任何后来的活动都会改写历史结论（**结论不可复现**）。
- **机制（待落）**：`TG-19` M-A——域必须由被判定物派生（该 Sprint 文档的锚点 + **该 Sprint 自己的**流水线 run），两端都取自该 Sprint 的记录；域不可派生 ⇒ distinct exit code `domain-unavailable`（fail-closed，**不得**退化成全域清单）。
- **反向对照**：① 复现 081 形态（追加更晚的作用域 run）⇒ 域仍可派生、不得产生 99 项；② 右端必须取该 Sprint 关闭期的最后一条覆盖 run（G2 期间的提交不得算进 Sprint-17）；③ 域不可派生 ⇒ rc=domain-unavailable 且**不打印 PASS**。
- **复用面**：所有"按窗口/时间域过滤"的闸门——**域的来源必须可追溯到被判定物**。

## 案例 8｜倒挂窗口静默 0 覆盖（`through < anchor` 既不点名也不贡献）

- **现象**：`anchor` 在提交序表内、而 `covers_through` **早于** `coverage_anchor` 时，窗口既不被点名、也不贡献覆盖 ⇒ **静默 0 覆盖**（"这个 run 审过了"这句话在读数上无法被证伪）。
- **证据**：复核 `074`~`079` backlog 小节（机制缺口 1）；真数据 17 个窗口里 0 例，且 `register`/`finish` 路径产不出该形态（只能由 `set-anchor --covers-through` 造成）。
- **根因**：**非法/退化输入没有专属判据**——落在"正常分支"之外，于是既不报错也不生效。
- **机制（待落）**：`TG-17` 条目 1——加具名判据 + 反向对照（构造倒挂窗口 ⇒ 必须点名）。
- **反向对照**：`set-anchor --covers-through <早于 anchor 的 sha>` ⇒ 必须具名 FAIL。
- **复用面**：所有"区间/窗口"参数——**每个退化形态（空、倒挂、越界、单点）都要有专属判据**。

## 案例 9｜关闭税读数手抄 ⇒ 抄成上一 Sprint 的数字，且**算术自洽**

- **现象**：Sprint-17 的关闭税读数被写成 `文档项 12`（8 must-fix + 4 should-fix）与"首轮 **19** 条必修/应修"。实测一查 `run-2026-09-25-doc-audit-070` 是 **8 + 3 = 11**，正确的合计是 **21**。`12 = 8+4` 与 `19 = 7+12` 都是**真数字**——只是属于 **Sprint-16**（其一查 `doc-audit-055` 恰为 8+4、代码 major 亦为 7）。两个 Sprint 的 must-fix 数**都是 8**，所以抄错后算术自洽，一查自己也没抓到。
- **证据**：`sprint-17.md` §9.5（计数口径 + 逐份报告实读 + 根因）；报告行号：`doc-audit-070:13-68`（Must fix 8 条）、`:72-78`（Should fix 3 条）；Sprint-16 侧：`2026-09-12-sprint-16.md:78,83`、其状态报告 `:11,88`。
- **根因**：**M1（关闭税）的头号指标，其读数没有任何工具**——只能手抄；而"同名指标 + 相邻 Sprint + must-fix 数相同"使抄错极难被肉眼发现。
- **机制（待落 → **已落 2026-09-25 D3**）**：`TG-19` M-E——读数由工具**从报告派生**（code 侧＝`## Graded findings` 的 graded 行数；文档侧＝`## Must fix` + `## Should fix` 的编号条数），关闭记录必须与工具输出逐字一致。执行点 = `verify/verify_close_tax_reading.py --sprint <doc>`（Sprint 文档带机读行 `关闭税读数: code_major=… code_critical=… doc_items=… 来源=<run_id>,…`）；规则条文 = `1-WORKFLOW.MD` §6 第 10 条。**实测**：工具派生的 Sprint-17 读数 `7/3/11` 与 `sprint-17.md` §9.5 的人工更正**一致**（人工复核 → 机器复核），改 1 个数字即 rc=1。
- **反向对照**：把记录里的数字改 1 ⇒ 必须 FAIL；在报告里增删 1 条 finding ⇒ 工具读数必须跟着变（防读死值）。**附带发现（本条即活体实例）**：同类既有判据 `verify_derived_numbers.py` 用"数字紧跟『断言』二字"来识别手抄的断言数，于是**步骤标识**（形如 `C2` 后接『断言』两个字）也会被当成计数——**本案例集第一版就是这样被自己的闸门拦下的** ⇒ 新判据须带消歧规则（前邻字符非字母数字），并各自带一条反例。
- **复用面**：凡"指标读数"——**读数必须能从产物机器派生，禁止手抄**；见 `1-WORKFLOW.MD` §6 的"派生数字不得手抄"。

## 案例 10｜死键放宽过宽 ⇒ 在"不存在的目录"下新增基线键 = 静默预留豁免

- **现象**：`verify_derived_numbers.py` 的"父目录不存在 ⇒ 判为分支差异"放宽，把"**分支本就没有**"与"**本分支上被整目录删除**"混为一谈：在 windows 的临时 worktree 里 `rm -r docs/iteration/pre-research` 后闸门仍 **rc=0**（修前是硬 FAIL）；更糟的是**在不存在目录下新增一个基线键 = 静默预留豁免**。
- **证据**：复核 `run-2026-09-25-code-review-080` finding **F2**（medium）；`TG-17` 条目 7。
- **根因**：放宽条件用了**间接证据**（父目录不存在）去代替**直接证据**（该路径在本分支的历史里是否存在）。
- **机制（**已落 2026-09-25 D5**；`TG-17` 条目 7）**：判据由"**父目录**是否存在"（间接证据）换成 `git ls-tree HEAD` 的**直接证据**——该文件或其目录在 HEAD 里存在、工作区没有 ⇒ FAIL（被删/死键）；两处都没有：旧键 ⇒ NOTE（真分支差异），**新键 ⇒ FAIL**（'在不存在的地方新增上限 = 静默预留豁免'，即复核指出的第二个洞）。反向对照 +4（J/K/L/M）。
- **反向对照**：在不存在目录下新增基线键 ⇒ 必须 FAIL；整目录删除 ⇒ 必须具名（两者都要真跑）。
- **复用面**：所有"分支差异/环境差异"型放宽——**放宽必须用直接证据，且列出它排除在外的形态**。

## 案例 11｜本期要求被**更早 Sprint 的同 role run** 借位满足 ⇒ 跨期假绿

- **现象**：`check_requirements()`（关闭闸门的需求侧判据）原先在**全账本**里找"某步骤跑过没有"，于是 `fanout.json` 声明的 `target='working-tree'` 是由**更早 Sprint** 的 run 满足的——Sprint-17 自己的 doc-audit run（`task_id='Sprint-17 close'`）**从来不符合**该 target，判据却一直绿。M-A 把判定域收到"本期"之后，这一项当场暴露（Sprint-17 的读数：99 项 → **1 项**，且这 1 项就是它）。
- **证据**：`verify/verify_close_readiness.py::check_requirements()`（新增 `window_start` 过滤）；实测输出：`[C1/需求] 步骤 2:doc-audit 缺 target='working-tree' 的 run（已有 task_id：['Sprint-17 close']）`；`agents/fanout.json::sprint_close_pipeline[1]`（`target: "working-tree"`）；跑法：`.venv\Scripts\python.exe verify\verify_close_readiness.py --sprint docs\iteration\sprint\2026-09-21-sprint-17.md`。
- **根因**：判据问的是"**有没有**这样的 run"，而不是"**本期**有没有"——域名不参与判定，等于把跨期证据当成当期证据。**"存在性"层面的判据最容易被历史数据喂饱**。
- **机制（已落）**：`check_requirements(..., window_start=...)` 只认本期窗口内的 run；域本身由 `sprint_identity_of_doc()` + `run_sprint_identity()` 派生（`TG-19` M-A）。
- **反向对照**：本期流水线未跑 ⇒ 逐条点名"缺 run"（自检内置，断言数以现跑末行为准）；**原始事故复现**：追加下一个 Sprint 的作用域 run ⇒ 上一个 Sprint 的窗口与问题清单**一字不变**。
- **复用面**：一切"有没有做过 X"的判据（评审跑过没有 / 闸门跑过没有 / 卡开过没有）——**必须问"本期内"**，否则历史会替当期作答。

## 案例 12｜收窄判定域时**顺手收窄了"存在性"判据** ⇒ 合法的跨期引用被判成假红

- **现象**：M-A 把 `check_c2`（指涉可核）的 run 名单换成"本期域"后，Sprint-16 与 Sprint-18 的读数里各多出 1 条 `[C2] … 的 scope 来源指向不存在的对象`——被引用的 `run-…-069` 属于**上一个 Sprint**，在域外但**在账本里确实存在**。
- **证据**：`verify/verify_close_readiness.py::check_c2(..., ledger=...)`（新增参数）；实测：改前 Sprint-18 读 6 项（含该假红）、改后 5 项且**全部真实**。
- **根因**：把两件事混成一个名单——"**本期该谁被要求**"（域）与"**这个名字在账本里有没有**"（全账本）。前者该收窄，后者**不该**。
- **机制（已落）**：`check_c2` 的存在性查找走 `ledger=`（全账本），而"谁被检查"仍走域内名单。
- **反向对照**：Sprint-16/Sprint-18 两条读数对比（域内查 vs 全账本查）；自检内含 M-A 反向对照 ①~④。
- **复用面**：任何"先按范围过滤、再对过滤后的集合查外部引用"的判据——**过滤范围与解析引用是两个判据，别共用一个集合**。

## 案例 13｜改了**生成物所依赖的元数据**却没重跑生成器 ⇒ CI 在"派生一致性"步骤红

- **现象**：为 `TG-19` M-A 改了 `verify/verify_close_readiness.py` 的 `VERIFY_META.features`（一句话），本地把该跑的闸门都跑了、**套件也全绿**，push 后 CI 的 step 7 仍红：`FAIL: TEST-MATRIX.MD 与脚本元数据不一致（脚本/元数据变更后须重新 derive）`（CI run `36124069452`）。修法 = `python verify/verify_matrix.py derive` 重生成矩阵（`09f0385`）。
- **证据**：CI run `36124069452` step 7 日志；本地 `verify_matrix.py check` 在改动后才复现同一报错（此前那次"CHECK OK"是在改 `VERIFY_META` **之前**跑的——**我把它当成了"改后也验过"**）。
- **根因**：把"生成物"当成了普通文件——**改了源（元数据）就必须重跑派生步骤**，而"我跑过闸门了"这句话对派生一致性**不构成证据**。同族形态：手抄派生数字（案例 9）、放宽路径（案例 10）。
- **机制（已落/待落）**：已落——CI 的 step 7 就是这条判据的执行点（**它抓到了**，说明机制有效，不是机制缺失）；本案例要治的是**我的操作顺序**：把 `verify_matrix.py check` 纳入"改了 VERIFY_META/注释型元数据"后的必跑清单（与 `derived_numbers` / `card-inventory` 同级）。
- **反向对照**：改 `VERIFY_META` 一句话、不 derive ⇒ `verify_matrix.py check` 必 FAIL（本次实测）；derive 后转 PASS（同时刻实测）。
- **复用面**：一切"由源生成的产物"（`TEST-MATRIX.MD`、`tg14-baseline.json`、`suite_result.json`、`prices.json` 派生价表…）——**改源就要重生成；本地绿 ≠ 派生一致**。

## 案例 14｜新函数插在**装饰器与它的函数之间** ⇒ 守卫挂错对象、被守卫的函数**裸奔**

- **现象**：为 `TG-19` M-A 收尾加 `_norm_sprint()` 时，我把它插在 `@_with_registry_lock` 与 `def cmd_register(...)` **之间**——装饰器于是挂到了 `_norm_sprint` 上。后果两条：① **`register` 丢掉了账本锁**（登记路径重新变成 last-writer-wins 竞态，正是 M10 当初加锁要治的形态）；② `_norm_sprint` 被加锁，而它在 `cmd_set_sprint`（同样加锁）内部被调用 ⇒ **同进程二次加锁**，Windows `msvcrt.locking` 重试 ~10s 后抛"锁获取超时"。表现为"新命令一跑就报锁被占用"，而裸锁、其他写命令（`set-anchor`/`set-output-chars`）全都正常——**症状指向锁，根因在装饰器**。
- **证据**：`set-sprint` CLI 实测 `锁获取超时… 被另一进程占用`（9.1s）；逐层排除记录——裸 `_registry_lock()` 三次连续获取均 0.0s OK；`cmd_set_sprint.__wrapped__(ns)`（绕过装饰器）**成功**写入；patch `_file_lock` 打 `traceback` 后栈显示第二次获取发生在 `cmd_set_sprint:834 | new = _norm_sprint(args.sprint)`，且调用者是 `wrapper:339`。
- **根因**：Python 装饰器与它修饰的 `def` 之间**不允许插入任何语句**——插入即"偷走装饰器"。而该错误**不会报语法错**，只会让守卫静默换人（本例里两处后果都是静默的：丢锁不可见、自锁只表现为超时）。
- **机制（已落）**：① 把 `_norm_sprint` 移到装饰器**之上**（恢复 `cmd_register` 的锁）；② **机检**——`verify/verify_agentops.py` 的 UC-22 里加了"8 条写命令必须都带守卫"这一条（子进程 + importlib 读真模块，不是读源码文本），**装饰器再被挤开就红**。
- **反向对照**：修前 `cmd_register` 缺 `__wrapped__`（丢锁）、`_norm_sprint` 反而带守卫（实测栈）；修后 `未加锁=''` 且 `set-sprint` 全路径通过（写入 + 留痕 + 同值无操作）。
- **复用面**：一切"用装饰器挂守卫"的机制（锁、审计留痕、权限、限流）——**守卫与函数的相邻性必须机检**；凡在两者之间插入代码的编辑，都要在同一提交里跑"守卫覆盖"断言。

## 案例 15｜机读行**没有行首锚定**：正文里一句同形叙述即可冒充真源（且缺行 = 放行）

- **现象**：`verify/verify_close_tax_reading.py` 的 `TAX_RE` 用 `search()` 且**无行首锚点**、`parse_tax_line()` 命中即 `return` ⇒ 在文档**底部**放真读数行的同时，在**更靠前**的正文里写一句 `…按 关闭税读数: code_major=7 … 的口径复算` 即可让闸门 `PASS`（实测 `rc=0`），而底部真行**一次都没被读**；docstring 自称"出现两行读数不放过"，但**"不放过"没有任何实现**。同族第二形态：**删掉读数行 ⇒ `SKIP` ⇒ rc=0**（"没写读数"被静默放行），而 `1-WORKFLOW.MD` §6 第 10 条要求"必须由工具派生"。
- **证据**：中途独立复核 `run-2026-09-25-code-review-083` major #1 与 minor（原话见报告 `verify_close_tax_reading.py:59` 与其 minor 条目）；探针实测两条：叙述句在前 ⇒ `CLOSE-TAX PASS`（rc=0）；叙述句写在前面且数字写成 99 ⇒ 判红并打印"声明 = code_major=99"（证明生效的确是**第一处**匹配）。
- **根因**：**机读行的"唯一性"没有被判定**——正则从"文本里出现"退化为"文本里含有"；而"唯一真源"是一个**计数判据**（恰好一行），不是**存在判据**。附带：`SKIP` 被用来表达"没写"（缺数据 ≠ 不通过）。
- **机制（已落）**：`TAX_RE` 加行首锚定 `^[ \t]*关闭税读数`；`parse_tax_line()` 返回**全部命中行号**，`>1` 一律 FAIL 并逐行点名；新增 `claims_closure()`——**自称已关闭**（声明真锚点 或 §9 有 run 行）却缺读数行 ⇒ **FAIL**，只有"没自称关闭"或"报告目录不存在（全新 checkout）"才是 SKIP。
- **反向对照**：自检 ⑦（正文同形叙述不计 + 两行 ⇒ 命中 2 行）、⑧（两条 `claims_closure` 判据各一例 + 负例）；真数据上仍 `CLOSE-TAX PASS`（Sprint-17 `7/3/11`），改 1 个数字 ⇒ rc=1。
- **复用面**：一切"机读行/标记行/单一真源"约定（`三查锚点:`、`关闭税读数:`、状态行）——**"唯一"必须实现为计数判据**；且**缺行必须有明确归属**（该 FAIL 的别 SKIP）。
- **注**：本案例的初版形态（`缺行 ⇒ SKIP`）是我在 M-E 交付时**自己写进 docstring 的"设计"**——复核的价值正在于"设计里的自述"与"实现里的判据"不一致时，只有读代码的人能看见。

## 案例 16｜判定域的**右端按登记时序**而非**覆盖远近** ⇒ 后登记的 run 可静默缩小判定域

- **现象**：`domain_right_boundary()` 取"域内 `started_at` 最新那条 run 的 `covers_through`"作为 C3 的上界。**后登记一条覆盖更少**的 run 就能把判定域拉回——与刚修好的**左端**（锚点被抬高致静默失明）是同一族、方向相反。自检里那条"域右端 b"**把该行为钉成了期望值**（把最新 run 的 `covers_through` 由 `SHA_D` 改成 `SHA_C` 并断言结果 `SHA_C`）⇒ 反向对照方向反了：它防住了"按 sha 字典序取最大"，却把"覆盖回退被接受"固化。
- **证据**：复核 `run-2026-09-25-code-review-083` major #2（判定点 `verify/verify_close_readiness.py:366`、消费点 `:1204-1205`）；现跑探针：`domain_right_boundary([早期 run(covers_through=dddd…), 更晚 run(covers_through=cccc…)])` → `('cccccccc…', 'run-late')`。
- **根因**：把**时间**当成了**覆盖**的代理变量（"覆盖随时间单调增长"是**陈述过的前提**，全仓无判据校验）。判据依赖未校验的前提 ⇒ 前提被打破时判据静默失效。
- **机制（已落）**：改按**真 git 祖先关系**取覆盖最远者（复用 `_is_ancestor`）；**不可比（分叉）⇒ 具名问题**（fail-closed，不猜谁更远）；`root=None`（夹具/无 git）时退回"登记时间最新"并**在问题里点名该口径**。
- **反向对照**：域右端 d——用两个**真实提交**（`HEAD`、`HEAD~1`）构造"后登记但覆盖更少"的 run ⇒ 必须选中覆盖更远者（原实现会选错的那个）；e——两条覆盖端点互不为祖先 ⇒ 具名问题。
- **复用面**：一切"取最新/最后/最大值"来界定范围的判据——**先问这个序关系是不是真的单调**；不是就把序关系写进判据（此处＝祖先关系），并把"不可比"变成具名结果。

## 案例 17｜"宽限"只有上界 ⇒ 未来时间戳的 run **永久**免检

- **现象**：§9 linkage 的在飞宽限判据写成 `age_min < grace`（`age_min = now - started`）。`started_at` 在**未来**时 `age_min` 为负、恒满足 `< 120` ⇒ "账本有 run 但 §9 未登记"这条判据可被一个未来时间戳**无限期**豁免（实测 `+70 年` ⇒ `problems=[]`）。而同一天另一处判据（`scope_window_problems` 的"窗口/未来"）对同一个未来时间戳是**具名 FAIL**——同一性质的数据两处判据不对称。
- **证据**：复核 `run-2026-09-25-code-review-083` major #3（判定点 `verify/verify_close_readiness.py:806-808`）；现跑两条探针：`started_at=2026-09-01` ⇒ 具名问题；`started_at=本机+70 年` ⇒ `problems=[]` 且打印"登记 -36792000 分钟前"。
- **根因**：**单向区间**被当成"在窗口内"；时间戳的**符号**没有判据。同类形态：负时长被当成"零耗时"（案例 5 族）。
- **机制（已落）**：宽限条件改为 `0 <= age_min < grace`；`age_min < 0` 走独立分支 ⇒ **具名 FAIL**（"未来的 run 不适用在飞宽限"），自检补对应反向对照。
- **反向对照**：未来时间戳必须**不被宽限吞掉**（具名）；宽限内（刚登记）仍只提示；超期仍 FAIL（三条并存，断言数以 `verify_close_readiness.py` 现跑 `EVIDENCE:` 行为准）。
- **复用面**：一切"宽限期/超时/新鲜度"判据——**区间必须双向**（下界同样要写），且"负值/未来"要有独立具名分支。

## 案例 18｜棘轮**名单**缺项 ⇒ 被漏掉的那张表继续发"静默配额"

- **现象**：`verify_gate_integrity.py` 的 `gate_integrity.ratchets` 只列 4 张棘轮，而它自己的 docstring 明写同族包括 `artifact_paths` 的动态目标上限 ⇒ `artifact_paths.dynamic_ratchet` **既不受"上限只许下调"约束、也没有 `measured_value`/`measured_at`、连 `measured_total` = Σ上限 的判据都不作用到它**；实测政策声明 `34 文件 / Σ107`、现跑 `34 文件 / Σ105` ⇒ `scripts/structure-guard.py`（5 vs 4）、`verify/verify_card_index.py`（2 vs 1）**各留 1 个"新增动态目标不报"的额度**。
- **证据**：复核 `run-2026-09-25-code-review-083` major #4（`agents/policy.json:105-148` 与 `verify/verify_gate_integrity.py:444-449`）；现跑 `verify_artifact_paths.py --report` 头行 `105 处 / 34 个文件` vs 政策 `Σ107`。
- **根因**：**机制的作用域由一张手写名单决定**——名单漏一项，机制对该项**完全不存在**，而"机制已在跑"的观感掩盖了覆盖缺口（与案例 3"空扫描集"同族：**作用域本身没有判据**）。
- **机制（已落）**：把 `artifact_paths.dynamic_ratchet.files` 补进 `ratchets`（`ratchets=5`），补 `measured_value`/`measured_at` 与两张表的实测快照（5→4、2→1），`measured_total` 重算；**待落**（复核建议）：加"棘轮表未被 `ratchets` 收录即 FAIL"的封闭世界判据，防止下次再漏。
- **反向对照**：`cap > measured_value` ⇒ FAIL（既有 L 例）；本次新增：该表的上限高于实测时**必须**被判到（修前完全不被判）。
- **复用面**：一切"名单驱动"的机制（棘轮表、守卫清单、`guard_required`、必跑闸门表）——**名单的完备性要有判据**（封闭世界自检），否则漏项等于静默失效。

## 案例 19｜"收尾当时才可写"的字段漏写 ⇒ 账本说做过、产物不见了，且**不可修** = 永久红

- **现象**：`finish --result-file` 是 `result_files` **当时**唯一的写入口。我给中途复核登记收尾时漏带该参数 ⇒ 账本记 `succeeded`、`output_chars` 有值，但 `result_files=[]`；而 `verify_ledger_measurement.py` 对**终态评审类 run** 严格判 `[missing_result_files_review]`（"评审结论不可回溯"）。重跑 `finish` 补救被拒绝——`非法流转 succeeded -> succeeded（finish 仅允许 running -> terminal）`——**这条 fail-closed 是对的，但它让该问题没有合法修复路径 ⇒ 闸门永久红**。
- **证据**：`agents/runtime/registry.json` 的 `run-2026-09-25-code-review-083`（修复前 `result_files=[]`）；`verify_ledger_measurement.py` 窗口内零违规判定（修复前报该条）；`finish` 拒绝二次收尾的实测输出。
- **根因**：**字段的生命周期与修复路径不匹配**——写入窗口只有一瞬，而判据在整个后续生命周期里都成立；缺口一旦发生就**只能靠改闸门或改数据**（后者被防双写机制有意禁止）。同族先例：`output_chars` 漏测（`set-output-chars`）、锚点写短 sha（`set-anchor`）——**每次都靠新增一个受控回填子命令解决，说明这是机制族缺口，不是单次手误**。
- **机制（已落）**：新增受控回填 `scripts/agent-ops.py set-result-files <run_id> --file … --reason …`——`--reason` ≥10 字符、**每个产物必须真实存在**（且只认 `agents/` 根一种口径，不做"仓库根也行"的宽容解析）、每次实际变更追加 `result_files_backfills`（`at/field/from/to/reason/by`）、**同值 = 无操作**（假留痕比无留痕更坏）；并纳入 UC-22 的锁覆盖探针。
- **反向对照**：`verify_agentops.py` **UC-23** 5 条——复现病根（漏带 `--result-file` 的终态评审 run）／回填成功 + 六件套留痕／同值幂等不留痕／产物不存在 ⇒ 拒绝且**不改库**／仓库根相对路径 ⇒ 拒绝。
- **复用面**：一切"只在某个时刻可写、但此后长期被判定"的字段——**要么把写入做成幂等可重入，要么提供受控回填口**；"不可修的红"最终会被当成噪音，或被更坏的方式绕过。

## 案例 20｜守卫**依赖人的记忆**（规则写了没执行）＋ 自动化脚本**没有前置条件**：注释被切碎而无闸门可见

- **现象**（一因两果，同一次 D4 批里连着发生）：
  1. **守卫有效但前提是"我记得跑"**：`structure-guard.py` 的快照档要求"编辑前先 `snapshot`"；2026-09-25 实测的 R1 第 6 次事故正是**跳过了这一步**（卡内 §7 的口径缝隙）。第二次复现就在本批：`edit` 出事故后**没有任何前置机制**会拦——直到提交时 CI。
  2. **自动化脚本用过期输入重跑 ⇒ 内容被切碎**：我用自动折行脚本处理超长行，第二次运行时**沿用了上一次的行号表**。行号已指向"折过之后"的短行，脚本于是从最后一个空格处继续切，把注释切成 `# 恒` / `# False，` 这类碎片（`verify_close_readiness.py` 的倒挂判据注释块整段损坏）。
- **证据**：① 提交被拒实测输出（`STRUCTURE-GUARD：提交被拒（结构守卫 rc=1）` + `docs/1-WORKFLOW.MD:299 标题被删：## 6. 规则与纪律…`，提交未产生）；`--replay-git` 9 条自检；② `%TEMP%` 备份（`*_backup.py`）与损坏后文件的对照；修复脚本三轮折行 37 行、E501 2537 → **2492**（上限 2494 未动）。两条都记在 `sprint-18.md` §10（带 `R1` + `编辑边界` 标记，供 `A-M12` 判据 ④ 复算）。
- **根因**：
  * ① **判据的前提由"人的记忆"提供** —— 快照是本地运行态，"拍没拍"在版本控制里看不见；这类守卫的失效不是"拦不住"，而是"**没人启动它**"。
  * ② **自动化脚本缺前置条件**（对输入不做"这一行确实需要处理吗"的检查）＋ **等价性判据选错**：我用了 AST 等价，而**注释不进 AST**，被切碎的正是注释 ⇒ 一路绿灯。
- **机制（已落）**：
  * **把前提换掉**：`structure-guard.py verify --from-git <rev>` —— 基线取自 **git**（已经存在的事实），与快照档同一套扫描口径；坏修订/取不到内容 ⇒ **rc=2**（旧写法会让基线为空集后打印 PASS）；有意删除必须写 `Structure-Removal: <路径> :: <理由≥10 字符>` **具名署名**（阈值入 `agents/policy.json::structure_ack_min_reason_chars`）。
  * **两层接线**：便利层 `scripts/hooks/pre-commit` ＋ `scripts/install-hooks.py`（`git config --local core.hooksPath scripts/hooks`，**零写盘**）；不可跳过层 = CI 按 push 范围跑同一条判据。**接线本身有判据**：`verify_gate_integrity.py::unskippable_guard_problems`——CI 调用/钩子模板/安装器任一缺失即 FAIL（机制的作用域必须有判据，见案例 18）。
  * **脚本层**：折行脚本加"当前行确实超宽"前置条件 + **逐字拼回等价**断言（注释/文档字符串/字符串三种模式各自的还原规则）+ AST 等价 + 逐段宽度；任一不满足即整行回退并点名。
- **反向对照**：`--replay-git` 9 条（干净放行／删标题必拦且点名／具名署名降级为可见 `[署名删除]`／同类删除无署名仍拦／坏署名 rc=2／3 种坏修订 rc=2）；钩子**真拦**一次（删标题的提交被拒、无提交产生）；接线判据 4 条。脚本侧：修复后的三轮折行中，被切碎的那类短行全部落在"前置条件"分支上被跳过（报告里逐行可见）。
- **复用面**：① 一切"需要人记得先做一步"的守卫——**把前提换成已经存在的事实**（版本控制、账本、产物），并把"启动动作"接进一个**每次都会发生**的入口（CI/提交）；② 一切**自动化改写脚本**——必须带**前置条件**（对当前输入成立吗）与**内容等价的独立判据**（而且要选**看得见被改对象**的那种：AST 看不见注释，就别拿它证明注释没被改坏）。

## 案例 21｜**验证动作自身用错了输入**：sha 从"别的仓库"派生 ⇒ 拿别人的 CI run 当自己的证据

- **现象**：D4 push 后我用既有的轮询脚本查 CI 结论。脚本按"`git rev-parse HEAD` → 用该 sha 过滤 run"工作，并有一条 fail-closed 检查（必须是 40 位十六进制）。**它报 `conclusion=success`**——但那个 sha（`133dc92…`）**不是我的提交**（我的头是 `c4fd255…`）：后台作业的 cwd 与主会话不同，`rev-parse` 于是在**另一个仓库**里取到了合法 sha，格式检查照样通过。**我的 D4 提交当时其实还在跑**（run `36148849228`，随后才是 success）。若就此收工，就会把"未验证"记成"已验证"。
- **证据**：轮询输出第一行 `HEAD = 133dc92648a7df11a9a0cf165fa810495ad265a2` 与 `git rev-parse HEAD`（在仓库目录内）=`c4fd255824cca64e7cdf925b936eca3dad724c4f` 不一致；按 **run id** 复查（`/actions/runs/<id>`）得到 `head_sha = c4fd255824cc…`, `branch = windows`, `event = push`, `conclusion = success`。
- **根因**：**判据的输入来自"环境"而不是"事实"**。`git rev-parse HEAD` 回答的是"**当前目录所属仓库**的 HEAD"，而脚本把它当成"我要验证的那次提交"。fail-closed 只查了**格式**（40 位十六进制），没查**归属**（这个 sha 是不是本次推送的）。与短 sha 事故同族：**"看起来对"的输入比明显错的输入更危险**。
- **机制（已落）**：验证脚本改为**只接受显式 run id**（`%TEMP%\dsh_ci_run.py`），并把 `head_sha`/`branch`/`event` 一并打印，供与预期**逐字比对**；sha 过滤那条老路径**不再作为收工依据**（若用，必须同时打印"这个 sha 从哪个仓库/分支解析出来"）。**规则条文**：`1-WORKFLOW.MD` §6 第 1 条（不手抄标识符）的**对偶**——**不猜标识符**：凡"用某个标识符去查结论"的动作，标识符必须要么**显式传入**，要么**连同它的来源（仓库/分支/事件）一起打印**。
- **反向对照**：用**错误 sha** 过滤 ⇒ 得到另一条 run（本次实测：结论 success 但 head 不是我的）；用 **run id** 复查 ⇒ `head_sha` 与本地 `git rev-parse HEAD` 逐字一致、`branch=windows`、`event=push`（两条都真跑，输出留档）。
- **复用面**：一切"按标识符取结论"的验证（CI run、账本 run、提交 sha、卡号）——**先证明这个标识符属于你要验证的那件事**，再取结论；验证脚本的输出必须包含**它自己的输入来源**。
