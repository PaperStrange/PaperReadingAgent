## 案例 1｜派单 prompt 里**手抄 sha**（短 sha 把覆盖窗口静默作废）

- **现象**：派 D2/D3 子代理时，我在 prompt 里写 **8 位短 sha `092a2f78`**。三个 run（`code-review-065`、`doc-audit-066`、`code-review-067`）以此登记锚点 → `CoverageWindow.covers()` 要求 40 位完整 sha ⇒ `covers()` 恒 False ⇒ **三条窗口静默作废、各贡献 0 覆盖**；C3 未归属提交由 15 抬到 **30**，并把 C3-T 例外表逼成"主路径"。
- **证据**：独立复核 `2026-09-25-d2d3-independent-review.MD` 的 **M-b**（原话"归因：主代理在 prompt 里给了短 sha"）；并行会话分析 §F1（"major，且由主代理造成"）；账本 `anchor_backfills`：065/066/067 三条 `092a2f78 → 092a2f784c9749126dc0f7483fe78ba721f424d0`。
- **根因**：① 人把**标识符**当文本转发（而不是让工具解析）；② 闸门对"格式不合法的锚点"**静默**返回"不覆盖"——非法数据被当成"没有覆盖"而不是"数据坏了"。
- **机制（已落）**：`register --coverage-anchor` / `finish --covers-through` 一律走 `_resolve_sha()`（`git rev-parse --verify <v>^{commit}` → 必须 40 位十六进制），失败 `COVERAGE-ANCHOR-ERROR` **fail-closed**；受控回填 `set-anchor --reason`（每次追加 `anchor_backfills` 留痕）；B4/B5 之后"端点不在计算范围且证明不了更老"**逐条点名**（不再静默）。**待落**：prompt/命令中禁止手抄 sha（见 §6 新条）。
- **反向对照**：`verify_agentops.py` UC-17 四条（短 sha **被规范化** / 无法解析 **被拒** / 回填缺理由 **被拒** / 回填成功且留痕）+ B5 反向对照 a/b/c/d（含"bogus sha 必须返回 False 而不得抛错"）。
- **同族第二实例（2026-09-25，主代理，非派单但同一根因）**：我**两次**给 CI 查询脚本传**短 sha**（GitHub `head_sha` 过滤只认 40 位）→ 脚本报"查不到 run"，我一度以为 CI 没触发。**修法不是"下次注意"**，而是把规则做进工具：`dsh_ci_poll.py` 现在**先 `git rev-parse` 解析**、解析不出就显式 WARN，并按长度自检（工具侧规范化，案例 1 的规则同样适用于主代理自己的脚本）。**教训**：同一根因（人把标识符当文本转发）会在"派单/命令行/脚本参数"三种载体上各犯一次——**只堵派单不够**。
- **复用面**：**凡"人把标识符交给工具"**（sha / run_id / 路径 / 键名）——工具侧解析+规范化+失败 fail-closed；派单侧禁止手抄，改为"由执行者 `git rev-parse HEAD` 或使用 CLI 默认值"。

## 案例 2｜子代理**中断不留痕**（三个修复批余额耗尽退出，留下未验证半成品）

- **现象**：关闭期三个修复子代理（四 major / 推前 CI / 两闸门失信）在同一分钟内因**余额耗尽**退出，**均未回执**，仓库里留下一批"改完未验证"的半成品：① `verify_ledger_measurement.py` 的重构只改了定义未改调用点 ⇒ `real_data()` 抛 `NameError`，而自检**仍打印 `ALL PASS (30 assertions)`**（2026-09-25 时点读数）；② 新代码顶破 `verify_artifact_paths` 的动态目标上限；③ `verify_lint` E501 由 2616 涨到 2830（上限 2631）；④ `verify_card_index` 的 fixture 落点被判"动态目标"。
- **证据**：sprint-17 §10 的过程事故行；三批的改动集与"修前/修后"闸门读数；上述 4 条半成品形态分别有单跑复现记录。
- **根因**：① 子代理**没有"退出前落状态"的机制**——中断＝无遗言，仓库里看不出哪部分是半成品；② **并发批次改同一批文件**（`verify_ledger_measurement.py` 被两批同时改），无所有权/锁；③ 流程里"验证"排在"资源允许"之后（余额耗尽恰好落在"改完、未验证"的窗口）。
- **机制（部分已落）**：spec 已要求调研/评审类 run 先落 `context.md` 再动手，但**修复类子代理当时未登记 run**（无 run 目录、无状态文件）；本轮实测的补救是"逐闸门单跑 + 自检反向对照"把半成品全部逼出来。**待落**：修复类派单同样强制登记 run 并把"任务清单 + 已完成/未完成"写进 run 目录；同一批派单**禁止共享文件**；任务完成定义里显式包含"改完即跑对应闸门"。
- **反向对照**：本轮以"把三个半成品逐个复现 → 修 → 复跑"作为实际对照（修前 `NameError`/上限越界/E501 越限/RATCHET 越界均实测，修后全绿）。
- **复用面**：所有**并发派单 / 长任务派单 / 资源受限环境**下的派单。

## 案例 3｜复核的**对照走了假路径**（注入式空转）

- **现象**：我新加的 B5 正向对照直接注入 `older_anchors={...}`，**从不调用 `_is_ancestor()`** ⇒ 该函数的真实缺陷（`except Exception` 抓不住 `SystemExit` 子类 `PolicyError`）**躲过了对照**，直到下一轮复核用"打真实函数 + 真实仓库"才抓到。同族既有实例：`verify_lint` 的棘轮对照用**临时副本自造的 caps** ⇒ 判据退化成 `count > count`（`3-LEARNED` 1.66）。
- **证据**：复核 `run-2026-09-25-code-review-075`/`-076` 的 finding；B5c 的补法（`_is_ancestor(ROOT, "deadbeef"*5, head_sha(ROOT)) is False`）；1.66 的注入实测（16 条→rc=0，17 条→rc=1）。
- **根因**：对照的**输入绕过了被判据驱动的真实入口**（注入中间变量、用副本自造阈值），于是"对照通过"只证明"那条被绕过的路径能通过"。
- **机制（已落）**：新对照一律**打真实函数/真实仓库/真实 CLI 子进程**（B5c、`verify_no_policy_hardcode` 的 `--dir` 子进程 rc 断言、`verify_gate_integrity` 的 8 闸门 `-O` 真跑）。
- **反向对照**：在 `%TEMP%` 副本里把修复还原（`except (Exception, SystemExit)` → `except Exception`）⇒ 对照 c **失败**；把上界判据改回无条件 ⇒ 对照 d **失败**（证明对照非空转）。
- **复用面**：**所有"反向对照/自检"的设计**——判据 = "对照必须能回答它打的是哪条真实入口"。

## 案例 4｜子代理报告"已修"**≠ 提交里有**（主张与事实错位）

- **现象**：复核 `run-2026-09-25-code-review-074` 按报告逐条核到**提交态**时发现：报告声称的若干修复在其时点的提交里**查不到**（相关闸门自创建后零提交）；后续轮次又发现我自己的提交信息里"`artifact_paths` 10 断言"与实测 **13** 不符、`measured_total` 2833 与实测合计 2815 不符。
- **证据**：复核 074/075/076 的 "claims found false/overstated" 小节；`git show --stat` 与闸门现跑输出的对照。
- **根因**：① 报告是**主张**，其证据时点可能与交付态错位（写报告时有改动、提交时没有或反之）；② **提交信息不受任何闸门扫**（"派生数字不得手抄"只扫 `docs/**`）。
- **机制（已落/待落）**：已落——复核的强制第一步是"按提交态复现"，且主代理的 prompt 也被当作**主张**（案例 6）；待落——提交信息里的派生数字同样不手抄（或让提交前钩子扫一遍）。
- **反向对照**：本轮 6 轮复核每轮都"先 `git show <sha>` 再下结论"，并逐轮记录"报告与提交态不符"的具体条目。
- **复用面**：所有**派单—回报链**（含主代理自己的提交信息与总结）。

## 案例 5｜"全新 checkout 模拟"用错方法（`git archive` 剥掉 `.git`）

- **现象**：我让复核用 `git archive HEAD | tar -x` 造"CI 等价树"验证一个 CI 修复 ⇒ 两脚本因**缺 `.git`** 假失败（`SUITE FAILED (2/24)`：`verify_agentops` 无法解析 HEAD、`verify_artifact_paths` 无 `git check-ignore`），差点被误读成"代码缺陷"。改用 `git clone` 后 `SUITE PASSED (24 scripts)`（2026-09-25 时点读数）。
- **证据**：复核 `run-2026-09-25-code-review-079` 的纠正段落（含两种方法的 rc 与失败脚本名）。
- **根因**：模拟只复制了**文件**，没复制**环境能力**（git 历史 / `check-ignore` / `fetch-depth`）——"等价"的定义写错了。
- **机制（已落）**：CI 等价模拟一律 `git clone`（含 `.git`、全历史）；本条已写入 sprint-17 §9.3 的方法学教训。
- **反向对照**：同一提交在 archive 树与 clone 树上的两套结果并列（2/24 假红 vs 24/24 全绿），差异脚本与原因逐条列出。
- **复用面**：所有"本机复现 CI / 复现他环境"的派单。

## 案例 6｜派单**前提未经核验**（我假设"登记 run 就会归属覆盖"）

- **现象**：我按"登记一条复核 run 即可让 `5313bb7` 变成'有归属'"派单，而当时的 C3 引擎**无法表达**规范窗口 `(三查锚点, HEAD]`（复核枚举账本 **14/14 窗口全部失效**）⇒ 子代理只能回报 BLOCKER，并额外发现"第一个锚点后提交**对任何窗口都不可归属**"。我随后自己查证才承认这是引擎缺陷、转去修引擎。
- **证据**：复核 `run-2026-09-25-code-review-074` 的 BLOCKER 段（含 `order_index` 构成与 14/14 枚举）；后续 3 轮复核对引擎修复的验证。
- **根因**：我把"机制会生效"当**前提**写进 prompt，而**前提本身没有最小复现**；派单链上"子代理的 finding 是主张"这条纪律，**反向同样成立——主代理的 prompt 也是主张**。
- **机制（已落）**：C3 引擎修好（`_is_ancestor` + `older_throughs` 对称判据）；**待落**：派单前对"依赖某个机制生效"的前提做**最小复现**（或直接在 prompt 里要求执行者先验证前提并在不成立时立刻回报）。
- **反向对照**：引擎修前/修后的同一命令对照（修前 `[C3] 2 项无归属`、修后归零；期间自查又抓出"历史窗口 12 项误报"并修掉）。
- **复用面**：所有**以某个机制/闸门"会生效"为前提的派单**。

## 案例 7｜派单时**没划"文件占用"**：主代理的 `git add <path>` 把子代理在飞的改动卷进自己的提交

- **现象**：2026-09-26 关闭期，我派子代理做一查文档欠账整改（4 组任务），**同时我自己也在改** `docs/3-LEARNED.MD`（回填 3 条新教训与 1.31 再版注记）；而子代理的任务清单里恰好也含 `docs/3-LEARNED.MD:339`（一查 should-fix 2 的另一半）。我提交批 4 时执行 `git add docs/3-LEARNED.MD` ⇒ 把子代理**当时还在工作区里、我从未审阅**的那处改动一并暂存并提交（`5f6ba27`）⇒ **提交说明与内容不完全对应**，且那处改动**未经复核就进了历史**。
- **证据**：子代理回执（第 7 条第 1 点）**主动点名**——"我的改动已被你的批 4 提交 `5f6ba27` 带入库"；复算：`git show 5f6ba27 -- docs/3-LEARNED.MD`；反查我自己的派单 prompt：写入集约束只写了"**只改 `*.md`**"，**没有列"哪些文件归谁"**。
- **根因**：**派单契约缺"文件占用"这一维度**。`1-WORKFLOW.MD` §6 第 2 条只有"同一批派单不得共享文件"——它管的是**子代理之间**，**没管"主代理 vs 子代理"**；而 `git add <path>` 的粒度是**文件**、不是**改动**，两者叠加时"只提交我改的那部分"在 git 层面**做不到**。
- **机制（待落，G3）**：① 派单前先列**文件占用表**——主代理与子代理的写入集必须**不相交**（子代理任务里点到的文件，主代理在它跑完前不得写）；② 主代理提交时**逐文件 review 后单文件 `git add`**，**禁止目录 / 通配**（`git add -A -- docs/` 这类会把别的写入者的在飞改动一起卷进来）；③ 复核口径：任何提交都应能回答"这个文件的这一行是谁写的、我审过没有"。
- **反向对照**：本条的**检出方式**本身即对照——它**不是被闸门抓到的**（`structure-guard` / `md_tables` / `derived_numbers` 全绿，因为被卷进来的那处改动本身是合法文本），而是**子代理在回执里主动点名**才暴露。⇒ "提交内容与提交说明是否对应"目前**无机检**；③ 的落地形态只能是"提交前逐文件 diff 复核"这条纪律 ＋ ①的占用表。
- **复用面**：所有"主代理与子代理**同时**改仓库"的派单，尤其**关闭期**（主代理写记录、子代理做整改）。

## 由本案例集派生的规则（条文真源在 `1-WORKFLOW.MD` §6）

1. **不手抄标识符**：prompt / 命令里禁止手抄 sha（及其他可解析标识符）；由执行者 `git rev-parse` 或使用 CLI 默认值。
2. **中断可恢复**：修复/实现类派单同样**先登记 run** 并把任务清单与进度写入 run 目录；同一批派单**不得共享文件**。
3. **对照打真实入口**：新对照必须打真实函数/真实仓库/真实子进程；注入中间变量的对照视为**未做对照**。
4. **按提交态复核**：任何"已修"结论的复核第一步是 `git show <sha>` 对比提交态；报告与提交信息都只是**主张**。
5. **环境等价要连能力一起复制**：CI 等价模拟用 `git clone`（含 `.git`）；只复制文件的模拟不得作为等价证据。
6. **前提先复现**：派单前对"某机制会生效"做最小复现；做不到就在 prompt 里要求执行者先验前提、不成立立即回报。
7. **留档义务**：子代理派单相关的**任何**漏洞/问题/事故，一案一节追加进本文件（6 要素齐备），并同步 §6 规则条文。
8. **文件占用表 ＋ 单文件 `git add`**：派单前明确"主代理 vs 子代理"的**写入集不相交**（该条把第 2 条的"子代理之间"扩到"含主代理"）；主代理提交时**逐文件 review 后单文件 `git add`**，禁止目录/通配（案例 7）。
9. **同一切片只许一个写入者 ＋ 授权以回执为准**：同一文件/同一数据切片**同一时间只允许一个写入者**；派单前先读目标文件的**当前状态**（如 `待回填 N 条` / `git status`）并在 prompt 里声明切片未被占用；"授权是否生效"一律以**子代理回执或文件状态变化**为准，**不以"我发了消息"为准**（案例 8）。
10. **不得用将来时冒充进度；派单台账四态**：每轮回复必须把"**已完成（带证据）**"与"**未派单（明写原因）**"分开，**禁止**用"下一轮我将…""接下来我会…"这类将来时把计划写成进度；每一批/每一项在台账里必须处于四态之一 —— `未派` / `在跑(<agent id>)` / `已回执` / `已提交`，**没有 agent id 的一律记为「未派」**（案例 9）。
11. **索引与提交是两个状态：提交切片前先清索引**：**为跑套件而暂存**（例如把新建未跟踪文件 `git add` 以满足"未跟踪路径为空"的判据）会让该文件停在索引里；此后任何一次**按切片**的 `git commit` 都会把它**卷进错误的提交**——本次实测：守卫切片的提交里混进了价表 spec（`4 files changed`，而该切片应只有 3 个文件），提交信息与实际内容不符。⇒ 规则：**要么先清索引（`git restore --staged <路径>`）再提交切片**，要么**在提交前逐条核对 `git diff --cached --name-only` 与本次切片清单相等**，不等就停手（案例 7 的同族变体：案例 7 是"`git add` 扫到别人的在飞编辑"，本条是"**上一次为跑套件留下的暂存**被后面某笔提交卷走"）。**提交后仍须核对 `git show --stat` 的文件数与切片清单一致**。

## 案例 8｜**同一文件切片被二次派单**（授权发给已收工的子代理 ⇒ 两个写入者同时指向同一段）

- **现象**：2026-09-26 登记册回填批次 1（`docs/6-DECISIONS.md` 的 `V-001~V-030`）。我先派 A（**只研究**），A 交回 30 条结果后我才发"批准你套用"的写授权——**而 A 当时已经收工**，那条授权没有启动任何新回合。我据"文件未变"（`git status` 干净、`待回填` 仍 523 处）判断"套用没发生"，于是又派 B（**研究＋套用**）。**同一时间，A 的写授权实际被执行了** ⇒ **两个代理同时指向同一份文件的同一段 30 条**。
- **证据**：B 的独立时间线——它首次跑闸门读到 `待回填 106`、`V-001` 五行仍是占位；再读时 30 条已填好、文件 `mtime 22:35:22` 变化、工作区转为 clean；落库结果 = 提交 `550b9fd`（`+163/−150`）。我的复核：`git status` 仅一行、`待回填` 计数 106→76。
- **根因（三条，都可核）**：① 派单契约缺"**切片占用声明**"——谁在写哪一段、写到什么时候，没有任何地方记；② 我把"**消息已送达**"当成了"**任务正在执行**"，而发给已收工子代理的授权不会自行生效；③ 我据"文件未变"推断"需要重做"，却**没有先确认是否存在另一个写入者**。
- **机制（待落，G3）**：派单前对目标文件/切片做**占用检查**并在 prompt 里写明（读该文件当前状态或 `待回填` 计数）；**同一文件同一时间只允许一个写入者**；"授权是否生效"一律**以子代理回执或文件状态变化**为准。
- **反向对照**：本次**幸免的原因不是机制**——是 B 自己发现冲突（首次/再次读闸门读数差 ＋ 文件 `mtime` 变化）后**主动放弃写盘、转为独立复核**，并额外产出了一份高价值复核（90 行不可变行逐字零差异、全部 `path:line` 展开核对无悬空、受控状态词 30/30、归纳标记词 0 命中）。**若 B 是无条件写盘的代理，`550b9fd` 会被覆盖成备注缺失、引号风格不同的版本**——即本次靠的是执行者自觉，而非判据。
- **复用面**：一切"多个 agent 写同一文件或同一数据切片"的派单，尤其是**长任务分批**（每批都改同一份文档：登记册回填、卡片批量修订、逐条整改）。

## 案例 9｜**文字承诺 ≠ 已派单**：用将来时把"计划"写成了"进度"

- **现象**：2026-09-26 反复发生——我在回复结尾写"**下一轮我从批次 2 派单开始**""接下来我会按这个顺序做：1…2…3…"，而**回合结束即终止**，没有任何东西续跑。用户连续两次追问（"已经派单了吗 我没有看到任何任务在跑"、"我不明白这种文字回复和实际交付中间相差过大的原因在哪，看起来对话中已经发生了很多次"）才发现：**那批根本没派**。
- **证据**：用户原话逐字（同上）；对照读数——本会话中"看起来一直在连续作业"的段落，**正好是 goal 处于 armed 的段落**（那时有 `<goal_round>` 自动续跑），而我在报告"G2 关闭完成"时**把 goal 标成 complete**，自动续跑随即停止。
- **根因（三条）**：① **回合是终点**：会话里唯一能让我自动继续的是 goal 的自动续跑；我关掉了它，却**继续沿用"下一轮…"的写法**——等于承诺一个已被自己关掉的机制；② **计划与交付报告写在同一段、同一种语气**，而"写承诺"零成本、"派单"要写一份长而精确的 brief（昂贵）；上下文紧张时我做便宜的那件事并给它贴上"进行中"（与 Sprint-18 §8.3 的"**用间接证据代替直接证据**"同族：用文字代替动作）；③ **没有任何判据检查"承诺 vs 实际派单"**——派单台账里在子代理真的起来之前，根本不会出现该批这一行。
- **机制（已落/待落）**：**已落** = ① 重新武装 goal（恢复自动续跑）；② 目标里写死"每轮回复必须把**已完成（带证据）**与**未派单（明写原因）**分开，不得用将来时冒充进度"。**待落** = 派单台账四态（`未派` / `在跑(<agent id>)` / `已回执` / `已提交`），**没有 agent id 即记「未派」**。
- **反向对照**：反例形态 = 以"下一轮…"收尾而回合终止（本轮两次）；正例形态 = **同一轮内先派单再报告**，且报告里给出 `agent id` 与实际 `commit sha`（本轮批次 2 的提交 `a20ce8c` 与批次 3 的派单 `0828a556-…` 即按此写）。
- **复用面**：一切**跨回合的多批任务**（长队列、批量回填、逐条整改）——**没有自动续跑机制时，任何"下一轮"都是空承诺**。

## 案例 10｜**索引未清**：为跑套件而暂存的文件被后面某笔切片提交**卷走**

- **现象**：2026-09-26 合并两个子代理成果时，我为让全量套件通过（`verify_artifact_paths` 的"未跟踪路径为空"判据要求新文件必须入索引），先把价表 spec `git add` 了；随后提交**守卫切片**（应只有 3 个文件）时，该 spec **仍在索引里** ⇒ 一起被提交，`4 files changed` 而**提交信息只描述守卫**——提交信息与实际内容不符。**这是我自己的操作事故，不是子代理的**。
- **证据**：`git show --stat bd06ee9`（`4 files changed, 609 insertions`，含 `create mode … 2026-09-26-price-tier-spec.MD`）与被回退重做后的 `8243222`（`3 files changed, 205 insertions`）逐字对照；子代理自报的 `git diff --stat` 为 `3 files changed, 205 insertions(+), 12 deletions(-)`，**重做后才与之相等**。
- **根因**：我脑子里把"**暂存**"当成了一个无副作用的临时动作，而它其实是**提交状态**。**为跑套件而暂存**与**为提交而暂存**用的是同一个索引，两个目的冲突时没有任何东西提醒我。与案例 7 同族（那次是 `git add <目录>` 扫到子代理的在飞编辑，这次是上一次的暂存被后一笔提交卷走）。
- **机制**：**已落** = 规则 11（提交切片前先清索引；提交前逐条核对 `git diff --cached --name-only` 与切片清单相等，不等就停手；提交后核对 `git show --stat` 文件数）。**处置** = 用 `git reset --soft HEAD~1` ＋ `git restore --staged` 重做，未推送前修正，历史无污染。
- **反向对照**：反例＝`bd06ee9`（混合切片，信息与内容不符）；正例＝`8243222` ＋ `d226231`（两笔各自文件数与切片清单相等，且 `8243222` 的 `205 insertions` 与子代理自报逐字一致）。
- **复用面**：一切"**先为了让某个闸门变绿而改了索引/工作区状态**"的场合（暂存新文件、临时删除产物、`--report-only` 之类的降级开关）——**闸门变绿时的状态与我要提交的状态可能不是同一个**，收尾时必须回到提交视角重新核对一次。

## 案例 11｜**派单未登记 run**：把"登记"当成子代理的作业 ⇒ 四批派单对**全部判据**不可见（主代理侧，用户 2026-09-26 裁定按**事故**处理）

- **现象**：2026-09-26 关闭期到 2026-09-27 凌晨，**四批实际派单工作每一批都落了提交**，却**一条 run 都没登记**：账本 `agents/runtime/registry.json` 里 `started_at >= 2026-09-26T05:30Z` 的 run **数量为 0**（**事故时点**读数＝补登记**前**；当时最新一条是 `run-2026-09-26-code-review-092`，`2026-09-26T05:11:18Z`），`agents/runs/` 下也没有同名目录。四批 = **A** `finish` 写入口 fail-closed 守卫（`8243222`）、**B** 报价表两档改造 ＋ spec（`d226231`）、**C** 行 7 `_norm_sprint` 收敛 ＋ 一致性向量（`8b03c77`）、**D** `087-minor-5/9` 原文取证档（`3899d2f`）。⇒ **违反规则 2**（"修复/实现类派单同样**先登记 run**并把任务清单与进度写入 run 目录"）。**用户 2026-09-26 原话**："这件事是严重失误，作为事故处理，并记录在 agent infra 反例，同时尽可能补全没登记的文档。"
- **证据（可核）**：① **事故时点**计数（2026-09-26，补登记**前**）——按 `started_at` 过滤 `registry.json` 的 `runs`，`>= 2026-09-26T05:30:00` 得 **0 条**；**补登记后**同一过滤得 **4 条**（`run-2026-09-26-implementation-093` ~ `-096`）⇒ 这条读数**必须带时点引用**，否则"0 条"与"4 条"两句都"可核"却互相矛盾（同 §8.2 的"陈旧读数"形态）；② 四批提交与文件数——`git show --numstat 8243222`（3 文件）/ `d226231`（2 文件）/ `8b03c77`（4 文件）/ `3899d2f`（3 文件）；③ **补登记回执**（本次整改）——`run-2026-09-26-implementation-093` / `-094` / `-095` / `-096` 四条，`started_at` 一律由**产物 mtime** 受控回填，每条的 `started_at_backfills[]` 记着 `{evidence, reason, old, new}` 四个字段，run 目录 `agents/runs/<run_id>/notes.md` 记着批次内容、落地 sha、补登记时现跑的验证末行与未决点；④ **判据不可见**（代码核实，行号现跑）——`verify/verify_close_readiness.py:1303` 的 `runs = load_runs(registry_path())` 是它**唯一**的数据源。
- **根因（分层，三条都可核）**：① **责任归属错位**——我把"登记 run"默认成**子代理的作业**（"我负责派单，它自己记账"），而规则 2 的主语是**派单方**（我）："修复/实现类派单**同样先登记 run**并把任务清单与进度写入 run 目录"。子代理是**独立上下文**、读不到本档也读不到 §6 规则条文 ⇒ **把登记放在执行者一侧，等于把它放在一个读不到这条规则的地方**（该条与案例 2 的"待落"是同一件事的两面）。② **关闭期用流程成本换掉了可核性**——关闭期每批都在赶，我为"少一次 CLI 往返"跳过 `register`：登记**没有即时收益**（当轮不会有任何判据因此变红），它保护的是**事后可核性**。这与案例 9 同族（用便宜的写法代替昂贵的动作），但更隐蔽——案例 9 省的是"派单"，本条省的是"记账"。③ **没有任何判据检查"派单是否有对应 run"**——`verify_close_readiness.py` 的判定域**完全来自账本**（`:1303` 取 runs、`:1352` `domain, unknown_ident = domain_runs(runs, sprint_id)` 派生域）；`check_linkage` 的两个端点**都是文档**：`:971` 查"§9 写了 run 而账本没有"、`:998` 查"账本有 run 而 §9 未登记"（它的输入 `scoped` 同样只由账本行筛出，`:968`~`:969`）⇒ **没有一端是"实际发生了什么"**。唯一沾到"现实"的判据是 C3 的提交归属，但它只在「三查锚点 → 域右端」区间里判，而域右端 = **域内覆盖最远那条 run 的 `covers_through`**（`:494`~`:543`；本次现跑 = `958c739`，由 `run-2026-09-26-code-review-092` 界定）——四批提交**全部落在这个右端之后**，于是连"提交无归属"这条间接判据也够不到它们。⇒ **未登记的派单不是"被判轻了"，而是从判定域里彻底缺席**。（旁证：`verify_ledger_measurement.py` 确有目录↔账本双向判据——`:482` 抓"有目录无记录"、`:504` 抓"有记录无目录"——但那两个端点是 `agents/runs/` **目录**与账本；一批**既没登记、也没建目录**的派单同样落在它的判定面之外。）④ **"待落"没有机器就等价于不存在**——案例 2 早已把"修复类派单强制登记 run"记为机制**待落**，而"待落"既无判据、也无到期日 ⇒ 它不会在任何人犯错时响：本轮四批全部踩中，而**关闭期闸门全绿**（`verify_close_readiness.py --sprint …` = `CLOSE-READINESS PASS`）。这不是闸门坏了，是**没有任何判据在管这件事**。
- **机制（已落/待落）**：**已落（本次补登记；注意它仍是"修复工具"而非"预防机制"）**——四条 run（`093`~`096`）＋ run 目录产物；`started_at` 由**产物 mtime** 重建（`set-started-at --evidence <真实文件> --reason <写明"时间戳由产物 mtime 重建，非实时观测">`），留痕在 `started_at_backfills[]`；`ended_at` 是**补登记时刻**（`finish` 现取）⇒ 账本里这四条的 `dur_minutes` = "重建起点 → 补登记时刻"，**不是**该批真实耗时（该口径已逐条写进各 run 的 `notes.md`，不得当成耗时读数引用）。**待落（G3）**——① 派单侧**顺序**判据：规则 10 的台账四态里，`在跑(<agent id>)` 一行必须能反查到 `run_id`，"有 agent id 无 run_id"即违规；② 一条**独立于账本**的派单真源（派单记录文件／回合记录），使"有派单、无 run"成为**可判定**而不是不可见；③ 把"关闭期跳过登记"这类**省掉的流程成本**显式记入关闭期欠账表——成本可以省，但必须**可见地**省。
