## 正文
**问题**：`agents/functions/` 下的 spec 用 `scope_required` / `coverage_window` 两个字段定义"这个 role 的 run 要不要声明 scope、承不承担内容覆盖"。现状只有**评审类** role 与主代理手册，**没有"实现类" role**，于是"执行实现工作的子代理"在账本里无处安放：挂评审 role ⇒ 被 C1 判"评审 run 没声明 scope"；不登记 ⇒ 该工作无留痕（`interrupt` 类事故也无法归因）。

**这是"判定域"问题，不是"多写一个文件"问题**：C1 的正确判据是"**该 role 的 spec 声明需要 scope 时**才要求 scope"，而"哪些 role 需要"必须来自数据（spec 的 frontmatter），不能来自代码里写死的角色名清单——否则每加一个 role 都要改闸门。

## 交付物（机制 M-D；按计划书 6 项标准交付：证据／根因／机制／反向对照／**在原始事故上验证**／复用面）
- **① `implementation` spec**：`agents/functions/implementation.md`，frontmatter 声明 **`scope_required: false`** ＋ **`coverage_window: none`**（实现工作不承担内容覆盖，只留痕）。
- **② `C2` 断言**：**账本中出现过的每个 role 都必须有 spec**（封闭世界；与 `policy.json::consumed` 的死键自检同族），spec 缺失 ⇒ FAIL 并具名 role。
- **③ `produced_only` 与覆盖解耦**：`produced_only: true` 的 run 不贡献内容覆盖（复用 `mark-produced` 的既有语义，不新开口子）。
- **④ 在飞宽限**：§9 linkage 的判定给"账本有 run 但 §9 尚未登记"一个**在飞宽限**，口径与 `ledger_measurement.terminal_writeback_grace_minutes` **同一取值来源**（不得各写一个数）；宽限内 WARN、超期 FAIL。

## 交付落地（2026-09-25 D2；含首次真实使用）

**① `implementation` spec（新）**：`agents/functions/implementation.md` —— `scope_required: false` ＋ `coverage_window: none`；正文英文（符合 `agents/README.md` 的 spec 语言约定），报告模板中文；`agent-ops validate-spec` PASS；`agents/README.md` 职能表同步（含"该 role 为什么存在"的说明）。
**② C2 封闭世界**：`check_c2` 的"无 spec 的 role"判据改为**按全账本**（`ledger=`）——判定域可以按 Sprint 收窄，"这个角色名有没有 spec"是关于**整个账本**的事实。
**③ §9 在飞宽限**：`check_linkage` 新增在飞宽限，取值**直接读** `ledger_measurement.in_flight.terminal_writeback_grace_minutes`（同一取值来源，不另写一个数）；宽限内打印 `INFO[linkage-in-flight]` **不计缺陷**，超期照旧逐条 FAIL。
**④ 机检与反向对照**（断言数以 `verify_close_readiness.py` 的 `EVIDENCE:` 末行为准，本批 +6）：域外野 role ⇒ FAIL；刚登记未写 §9 ⇒ 只提示；超期未写 §9 ⇒ FAIL；真政策三条（spec 被装载 / 不是评审类 / 真账本 role 全部有 spec）。

**首次真实使用**：`run-2026-09-25-implementation-082`（role `implementation`，`sprint=18`，报告见 `agents/runs/run-2026-09-25-implementation-082/implementation.report.md`）。实测两点：① 它**不进入** §9 登记要求（`implementation` 不在 `close_ledger_steps` 的 role ∪ `review_roles` 里）——这正是"实现工作不该被当评审 run 点名"的落地；② 它**不贡献 C3 覆盖**（Sprint-17 读数仍为 **1 项真项**，其中不含任何 implementation 项）。

**真实使用当场暴露并修掉的 M-A 缺陷（单列）**：`domain_right_boundary()` 原先只看"域内最新一条带 `covers_through` 的 run"——而实现类 run 在 `finish` 时会**自动记下空窗口**（`covers_through = 登记时 HEAD`）⇒ 它把 G2 的域右端错误地拉到了自己的提交上。修法：新增 `_contributes_coverage()`，排除三类不承担内容覆盖的 run（`produced_only`、spec 声明 `coverage_window: none`、以及作用域类 role），并补两条反向对照（域右端 d/e）。**结论一句话：空窗口不是覆盖声明，不能当边界用。**

**残留**：`mark-produced`（老路径）与 `implementation`（新路径）的 A/B 对照留到 G2 关闭期的某个实现批；本节只声称"新路径可用且被机检覆盖"，不声称两条路径已对拍。

## 验收判据
① `implementation` spec 存在且两个字段有值，且**被闸门消费**（不是只写文件）；
② 以 `implementation` role 登记一条 run ⇒ C1 **跳过**（不是 FAIL）、C3 **不计覆盖**（反向对照：评审 role 同样登记 ⇒ 两条判据都照旧判）；
③ 账本里出现一个无 spec 的 role ⇒ FAIL 且具名（反向对照：补上 spec 后转 PASS）；
④ §9 linkage 的宽限：评审 run 登记后不填 §9 ⇒ 宽限内 WARN、超期 FAIL（两条都要实测）；
⑤ **在原始事故上验证**：`run-2026-09-25-code-review-068` 型（实现工作挂评审 role）在修好后的判定域里**不再产生假红**，且其覆盖字段仍一字节未动。
