## 正文
`scripts/agent-ops.py` 早已支持 `--usage-in/--usage-out/--usage-cache-read/--usage-cache-write`，但 `agents/runtime/registry.json` 里 **99 条 run 只有 8 条带 `usage`**（且都是夹具数字）⇒ **真实工作一条 usage 都没有**，成本**无法按 run 归属**。

后果：反例档的实际损失只能从会话日志按时间窗／步段反推，**分段规则靠人判**（案例 12 明写 ±2.3 倍不确定度）。

**方向**：`finish` 时从会话日志自动带入 usage，或至少强制显式声明「本 run 未记 usage」。

**验收**：新增 run 的账本行带真实 usage，且「某批花了多少」可由账本直接算出。

## 2026-10-28 进展：派单计数改账本口径（与预算闸门同源）＋读数收到本会话

时点口径：下文读数全部来自 **2026-10-28（R2 网络日期）** 的现跑，属**时点读数**，
不得当日后的现值引用。

### 缺陷（读码定位，不看注释）

1. **计数式与扫描面错位**。`scripts/spend-report.py::check()` 的派单数是
   `dispatched = len([1 for name, _ in rows if not name.startswith("session-")])`，
   而 `rows` 来自 `SESS.rglob("*.jsonl.zstd")`，`SESS = ~/.dsh/sessions` —— **全机所有
   cwd 桶**。于是判据是「**目录名形状**」、作用域是「**整台机器**」。
2. **三种误算**：①别的主线／别的项目的子代理目录（裸 `<uuid>/`）被算成"本仓派单"；
   ②旧布局里主会话目录也是裸 `<uuid>/`（本机 `--D-All-Downloads-PaperReading--` 桶里
   绝大多数的裸 uuid 就是这种）⇒ 主会话本身被当成派单；③"本会话"与"别的会话"
   **在代码里没有任何区分维度**——`main_sessions` 只被 output 轴用到，计数轴一次都没读。
3. **两个派单数**：`scripts/agent-ops.py register` 的派单预算闸门读的是
   `agents/runtime/registry.json` 当日登记数，度量仪读的是目录名形状 ⇒ 同一天两个数，
   而 `agents/spend-budget.json` 自己早就写着「不拿度量仪那个数当阻断依据」。
4. **金额轴同源缺陷**（修作用域时发现）：同一会话目录下并存
   `session.jsonl.zstd`／`session.v3…`／`session.v4…`，三者是**累积重放**
   （首记录逐字相同、末记录递增到当下）⇒ 旧实现全读＝按文件数重复计价。

### 修法

1. **计数只来自账本，并且调用真源而不是照抄算法**：`agent_ops()` 用 `importlib` 加载
   `scripts/agent-ops.py`，`ledger_reading()` 调它的 `_dispatch_reading(data, day)`；
   账本路径取它的 `REGISTRY_PATH`（跟随 `AGENT_OPS_DIR`），"今天"取它的 `_local_date()`。
   ⇒ **算法／账本／日期**三个要素全部同源，本文件里没有第二份计数算法。
2. **预算也同源**：`check()` 的预算文件改读 `_spend_budget_path()`（跟着账本根走）。
   原文案自述"预算与账本必须同源"，而旧代码写死 `ROOT/agents/spend-budget.json`。
3. **日志口径只做两件事**：费用折算 ＋ 一条**只报**的对账读数。归属维度＝日志**头记录
   的 `parentSession`**（父链可达 `main_sessions`；旧布局的物理嵌套也算）——这条**可从
   数据判定**，不再依赖目录名形状；选它的理由是：它是唯一由运行时写进日志的父子关系，
   与目录命名习惯无关，换 DSH 版本也不会变。
4. **每会话只取最新一份日志**（`session_files()`），修掉累积重放的重复计价。
5. **判决表拆两类行**：`block`（账本派单／主代理 output／全机 CNY——判据面一字未改）与
   `report`（本会话派单／本会话 CNY——无预算、无基线、**不参与退出码**）。
   金额轴**没有**从判据改成只报（那会是放宽判据；`budget` 段现值一个都没动）。

### 两条口径如何同源（不是"看起来像"）

- 判据行 `派单会话数/日（账本）` ＝ `register` 闸门打印的 `dispatch-budget: N/6` 里的
  **同一个 N**：同函数（`_dispatch_reading`）、同账本（`REGISTRY_PATH`）、同 UTC+8 日
  （`_local_date`）。闸门的并集读法（`run_id` 日期段 ∪ `started_at` 折算）**照用不另选**
  ——另选一种就等于造第二个数。
- 现跑对照：`register` 打印 `dispatch-budget: 2/6` 的同一时点，`spend-report --check` 的
  账本行读数为 2；`verify/verify_spend_report.py` 把这条钉成**双进程断言**（一个进程现算
  `agent-ops` 的函数，另一个进程跑度量仪，两数逐字相等）。
- 日志口径**不参与**判据，只与账本**对账**：相等则打印"两口径一致"；不等则点名差额与
  候选会话（差为正＝账本未登记的派单；差为负＝账本里并非本会话的登记）。**不许静默取其一**。

### 反向对照（真驱动）

夹具：`%TEMP%` 合成树（假账本＋假会话树），用 `AGENT_OPS_DIR`／`SPEND_SESSIONS_ROOT`
把**同一份代码**指过去；"修前"＝`HEAD` 里那份 `spend-report.py` 的**原样副本**，只把
`SESS` 根指到目标树，其余逐字未改。另有两条对照在**真树**上做（写进真
`~/.dsh/sessions` 后立即删除，删后已核验不复存在），因为跨 cwd 桶才是旧缺陷的真正范围。

| 对照 | 修前（原样副本现跑） | 修后（现跑） |
|---|---|---|
| 真树基线（本会话 3 个子代理） | 派单 3 | 账本 3／本会话 3，**一致** |
| ① 真树加一个**别的项目**的子代理目录 | 派单 3 → **4**（算进来了） | 账本 3／本会话 3（**不动**）；只有"全机 CNY"涨 |
| ② 真树加一个**本会话**的子代理目录 | 派单 3 → 4 | 本会话 3 → **4**（账本不动 ⇒ 差 +1 并点名） |
| ③ 夹具：本会话 1 笔＋别的会话 1 笔 | 派单 2 | 账本 1／本会话 1 |
| ④ 夹具：再补一个别的会话子代理 | 派单 3 | 本会话仍 1（修前算法在同一夹具上数 3＝**真阳性**） |
| ⑤ 夹具：账本补到 2 笔（同一时点） | — | 账本 2 ＝ 本会话 2，**一致** |
| ⑥ 真树历史窗口（`--days 40` 全机合计） | 514.16 元（三份日志重复计价） | **376.57 元**（每会话一份） |

真阳性为什么必须给出：如果不证明"修前的算法在同一夹具上确实会数进来"，那么"修后不算"
可能只是夹具本来就数不到——那条断言就是空转。冻结副本（`prefix_reading`）因此在
`verify/verify_spend_report.py` 里常驻。

### 残余风险（金额仍不可作阻断依据的理由）

1. **模型名不在事件里**：计价按 `--model` 假设（缺省 `deepseek-flash`）；实际计费模型
   不同则整个读数按倍率缩放 ⇒ 金额是**估算**，不是测量。
2. **单价／档位／汇率都是外部数据**（`agents/runtime/prices.json` 的 `_tiers` 与
   `meta.fx_usd_cny`）：价表刷新、跨档切分、汇率变动都直接改结论 ⇒ 拿它阻断＝把估算
   误差变成停工。
3. **账本 `usage` 缺口未修**（本卡正题仍在）：真实花费只能从日志反推，而日志侧新加的
   "每会话只取最新一份"依赖"`session.vN` 是累积重放"。这条**已按日核对**：三份日志的
   逐日 usage 读数完全相同（v0 == v3 == v4），且 v4 ⊇ v3（逐日）⇒ 只取最新一份不丢
   usage；反过来按文件数全读会把同一批调用计 2～3 次（真树 `--days 40` 的差额即由此来）。
   仍未覆盖的是"将来某个版本改成增量写"——那时这条假设会**静默少算**，没有判据盯着。
4. **账本行没有 `session_id`／`agent id` 字段** ⇒ 两条口径只能比**数量**，不能逐笔对账；
   对账行给出的只是"候选会话"，无法指名到底哪一笔没登记。要逐笔对账得给账本加字段
   （`scripts/agent-ops.py` 不在本卡授权写入集内，列为下一步）。
5. **同仓并行批**：账本口径是"本仓当日登记数"（闸门也这么算），同一仓库里另一条主线的
   登记会一起计入；本会话口径不含它们 ⇒ 两口径出现**负差**是预期形态，不是 bug。
6. **金额轴的现状与裁定**：`--check` 里金额行**仍参与退出码**（`docs/1-WORKFLOW.MD` §6
   第 17 条原文要求"超预算非零退出"）；`register` 闸门则从不读金额。本批**没有**把金额
   改成只报——那需要同批改第 17 条原文，不在本批授权写入集内。**不能**用金额决定"今天
   还派不派单"，理由就是上面三条（估算而非测量）。
