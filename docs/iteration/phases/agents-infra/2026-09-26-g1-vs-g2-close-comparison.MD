### 1.3 时间口径（UTC / UTC+8 / 本机 +09:00 三者不同，必须先说清）

- `agents/runtime/registry.json` 的时间戳是 **UTC**（形如 `"started_at": "2026-09-25T04:48:10+00:00"`，见 `agents/runtime/registry.json` 的 run 记录字段）。
- 仓库文档统一用 **UTC+8**（`docs/iteration/sprint/2026-09-25-sprint-18.md:228` 专门更正过一次"UTC 与 UTC+8 被写成同一个数"）。
- **本机的系统时区是 +09:00，不是 UTC+8**（实测 `(Get-Date).ToUniversalTime()` 与 `Get-Date -Format o` 相差 9 小时）；
  因此 **`git log --date=local` 的显示值比仓库文档的 UTC+8 大 1 小时**。
  ⇒ 本文件**全部用 commit epoch（`%ct`）换算 UTC+8**，不用 `--date=local`。
  **这条本身是一个坑**：任何人直接抄 `git log --date=local` 的输出，都会得到与本文件不符的时间。
- 换算示例（可复核）：`run-2026-09-25-impact-assessment-085` 的 `started_at = 2026-09-25T16:51:49+00:00`
  → UTC+8 = **2026-09-26 00:51:49**；这正是 `2026-09-25-sprint-18.md:228` 那次更正的结果（原文误写 `16:51 UTC+8`）。

## 9. 结论：G2 相对 G1 是更慢 / 相当 / 更快

### 9.1 分阶段回答（两批的阶段表现正好相反）

### 9.2 差异的主要来源（按可核证据强度排序）

1. **关闭期的"合格"标准在执行中被换掉了（最大来源，且这是"标准变化"不是"效率变化"）**。
   可核事实链：G2 的关闭三查判出 30 行发现（与 G1 同量级，甚至更少）；
   但 G2 把**修复验证复核常态化**（批 1+2 → 批 3 → 批 7；`2026-09-25-sprint-18.md:215`~`:218`），
   并把用户 2026-09-26 的裁定"**主代理自定的债口径不可信、予以撤回**"落为"**一查/二查判出的未闭环项仍属关闭阻塞项**"
   （`2026-09-26-g2-close-retro.MD:8`~`:10`、`:71`~`:75`）⇒ 关闭期结束时有 **18 项未闭环**全部保持阻塞（`:95`~`:116`）。
   **G1 没有这一步**：G1 的关闭阻塞项（21 条）在审阅期内闭环后即由修复验证复核确认收口（`2026-09-21-sprint-17.md:197`）。
   ⇒ **同一批发现，G2 被要求"逐条闭环或由用户逐条豁免"，G1 被要求"审阅期内修掉即闭环"**——**门槛不同**。
2. **修复返工（G2 侧最硬的一项，且与规模无关）**：关闭期提交 **41 对 20**，独立验证 run **3 对 7**；
   G2 关闭期还发生了"**修法本身没生效**"的一例（`run-…-091` 判 critical，`2026-09-26-g2-close-retro.MD:35`、`:48`）——
   即**同一处被修了两次还没修对**。retro §3 自查比例 6:4（修复不合格 : 真耦合）。
3. **判定域缺陷造成的返工**：G2 的第一交付物 `TG-19` M-A 修的正是"Sprint-17 关闭读数由 1 项变 **99** 项（其中 98 假红）"

   ⇒ 这条**同时是 G2 的产出与 G2 的耗时来源**：修复前 G2 自己的一条读数不可用。
4. **人力介入次数**：G2 关闭期用户介入了**两轮**实质性裁定（撤回债口径、要求"我需要真实"），
   逐字原话 13 条（`2026-09-26-g2-close-retro.MD:79`~`:93`）；G1 关闭期用户裁定集中在一次签核（`2026-09-21-sprint-17.md:188`~`:195`）。
