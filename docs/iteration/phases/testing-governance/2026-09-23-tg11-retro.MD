## 4. ④ 闸门自身的验收（反向对照，全部实测）

`verify/verify_close_readiness.py` 的自检即**六个反向对照场景 + 三个边界**，逐条断言"坏输入必须 FAIL、好输入必须 PASS"：

| 场景 | 期望 | 实测 |
|---|---|---|
| 合规（锚点干净） | PASS | ✅ `problems=[]` |
| 省掉〇查 | FAIL | ✅ `① 账本中没有〇查 run` |
| 二查只有 windows | FAIL | ✅ `② 二查缺少 main 分支任务` |
| 二查 `self-chosen` 无 deviation | FAIL | ✅ `④ …自选范围但未声明 deviation` |
| **锚点之后存在未评审提交（本次事故最小复现）** | FAIL | ✅ `⑥ 三查锚点之后存在未评审提交：…` |
| §9 写了 run 但账本无 | FAIL | ✅ `⑤ §9 写了 run 但账本无记录` |
| 账本有 run 但 §9 未登记 | FAIL | ✅ `⑤ 账本有 run 但 §9 run 表未登记` |
| 未声明三查锚点 | FAIL | ✅ `⑥ 未声明三查锚点` |
| `--sprint` 指向不存在的文档 | 退 2 | ✅ `CLOSE-READINESS-ERROR`（fail-closed，不静默放行） |

**CLI 闸门的反向对照**（未修复实现 = `HEAD` 版 `scripts/agent-ops.py`）：
无 scope 来源的评审 run 被**放行**（`rc=0`，直接 `registered`）；`--scope-source` 被当成**未知参数**（`rc=2`）

## 7. 教训（定稿三条，关闭期由 `lessons-learned` 统一编号入库；**期中不插入**以免 "49/63" 口径漂移）

1. **有规则 ≠ 有执行点**：规则若没有"触发时机 + 检测装置"，其强度等于主代理当时的记性；本次**两份**文字规则同时被绕过，唯一生效的是**用户追问**。
2. **任务分类先于规则检索**：规则挂在「阶段」（关闭）语境、违规发生在「动作」（修复后复核）语境 → 分类不命中则检索不到。
   → **规则必须挂在动作上，或由闸门代检**（本卡 M1/M2 即此形态）。**2026-09-23 的日期漂移是同一根因的第二实例**（规则在 §3 且刚被引用，仍未检索）。
3. **"已完成"的检查项会过期**：三查跑过 ≠ 三查有效；任何一次性检查都必须记录**锚点**（覆盖到哪个 commit）与**失效条件**，并**机器可判定**。
4. （新增，2026-09-23）**派生事实（日期/数字/状态）必须有 SSOT 与重生成机制**：手抄型"事实"必然过期，且**过期无告警**——归 `TG-12`；日期类判据（文档日期 ↔ committer 日期）应做成 lint。
