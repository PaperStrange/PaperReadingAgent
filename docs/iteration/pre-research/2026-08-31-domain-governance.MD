# 领域治理备忘：多领域方案讨论的同一流程 + 独立 subagent（domain-governance）

> 状态：**设计备忘，未实施**（2026-08-31，用户指示"现在不需要立即创建这些 subagent"）。本笔记是未来 product-research / marketing-research 上线时的强制上下文输入。
> 归属：`docs/iteration/pre-research/` 根目录（跨领域治理，非单一领域笔记）。注入规则见 `1-WORKFLOW.MD` §4.4。

## 1. 背景与用户要求

- 产品完整生命周期将有**技术 / 产品设计 / 营销推广**等多条方案讨论线（2026-08-31 用户提出）。
- 要求①：各领域讨论与当前技术方案**保持相同流程**（预研探讨 → 笔记落盘 → 用户决策记录 → 规划管线注入，见 §4.4「预研上下文传递」）。
- 要求②：调研时**注意各自的侧重点**，**各自维护一个独立的 subagent**，不得相互混用——否则结论追溯链路不清晰、事实真相不可察。
- 要求③：从本事项起，主代理**主动思考、主动完善协作方式**（记录在案，见 §5）。

## 2. 设计原则：一领域 = 一 agent = 一账本 role = 一笔记目录

| 领域 | agent 角色（spec 名） | 调研侧重点 | 预研笔记目录 | 状态 |
|---|---|---|---|---|
| 技术 | `tech-research`（spec v1.1.0） | 技术可行性、选型/对比、架构、最佳实践、成本/风险 | `docs/iteration/pre-research/tech/` | ✅ 已上线 |
| 产品设计 | `product-research` | 用户需求与痛点、竞品分析、UX/交互验证方法、需求优先级 | `docs/iteration/pre-research/product/` | ⏳ 待产品线讨论启动时创建 |
| 营销推广 | `marketing-research` | 市场定位与细分、渠道策略、定价、内容策略、合规约束 | `docs/iteration/pre-research/marketing/` | ⏳ 待营销线讨论启动时创建 |

**隔离规则（不得混用）**：
- 每个领域一个 spec（由 `agents/functions/_template-agent.md` 复制填写，英文，跑 `validate-spec` 后上线），**一个账本 role**——run/成本/结论按 role 分离，dashboard /costs /runs 可独立追溯。
- 每个领域一个笔记目录，结论只落本域目录；**跨领域引用必须注明来源笔记/报告与所属领域**，不得把 A 领域的结论直接当作 B 领域的事实。
- 规划管线按领域路由（未来 fanout v4 设想：research 步按任务领域选择对应 spec；当前仅 tech-research 一条，product/marketing 讨论出现时再加步/参数化，**由用户批准后实施**）。
- 领域边界有争议的问题（如"功能定价"同时涉及产品与营销）→ 由**用户裁决归属**，或明确拆成两条子问题分别入两域。

## 3. 上线判据（何时创建，而非现在）

- 触发：用户启动对应领域的第一轮方案讨论时。
- 步骤：① 复制模板建 spec（frontmatter 五段式 + 可配置参数，侧重点按本备忘 §2 表定制）；② `validate-spec`；③ 建笔记目录 + 在 `pre-research/README.md` 索引登记；④ fanout planning_pipeline 增领域路由（用户批准）；⑤ 首跑演示 run 入账本。

## 4. 与现有机制的关系

- 依赖：`1-WORKFLOW.MD` §4.4（预研上下文传递）、`agents/fanout.json` v3（pre_research 注入）、tech-research spec v1.1.0（Baseline Alignment）。
- 本备忘即"预研笔记作为规划管线上下文"机制在**跨领域场景的扩展设计**，本身不改变现状代码/配置。

**协作改进提案（主代理主动提出，用户裁决采纳/否决/搁置）**：
1. 决策追溯索引：`pre-research/README.md` 汇总全部笔记 × 决策点（本轮已落地）。
2. 讨论收尾固定动作：每轮方案讨论结束时，主代理输出「决策点清单 + 待办 + 建议下一步」，下轮开始先对齐再继续。
3. 里程碑复盘槽位：每次 sprint 关闭/阶段讨论收尾，主代理主动提 1 条协作改进建议供用户裁决。
